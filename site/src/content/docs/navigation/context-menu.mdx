```svelte
<script>
  import { ContextMenu, DropdownMenuItem, DropdownMenuSeparator } from "@codeatlasdev/ui";
</script>

<ContextMenu role="group" aria-label="Project file">
  quarterly-report.pdf
  {#snippet menu()}
    <DropdownMenuItem onclick={rename}>Rename</DropdownMenuItem>
    <DropdownMenuSeparator />
    <DropdownMenuItem variant="destructive" onclick={remove}>Delete</DropdownMenuItem>
  {/snippet}
</ContextMenu>
```

`ContextMenu` wraps a region and opens a [DropdownMenu](/docs/navigation/menu/) at the pointer. The `menu` snippet takes the same items: `DropdownMenuItem`, checkbox and radio items, `DropdownMenuSub`, labels and separators, with the same keyboard support (arrows, Home, End, typeahead, Enter or Space, Escape, ArrowRight and ArrowLeft for submenus).

Three triggers open it. A right-click opens it at the pointer and cancels the browser's own menu; a second right-click moves it. A touch that stays put for `longPressDelay` (500 ms) opens it at the finger; lifting early or dragging more than 10 px cancels the press, and the browser's own long-press menu is cancelled. Shift+F10 or the ContextMenu key on the focused region opens it at the region's start, on the first item. Escape closes it and focus returns to the region.

The region is focusable by default (`tabindex="0"`) so the keyboard trigger is reachable; set `focusable={false}` when the region already contains its own focusable target (a row with a link) and put the handlers' role there. Give the region a `role` and an `aria-label` through the rest props when it is not plain content. A context menu is never the only way to reach an action: keep the same actions on a visible button, for example a [DropdownMenu](/docs/navigation/menu/) trigger.

Text fields (`input`, `textarea`, `select`, editable content) keep the browser's menu (copy, paste, spellcheck); `disabled` keeps it everywhere. `bind:open` and `onOpenChange` work as on `DropdownMenu`.
